DeepResearch：把报告当成可以被反复检索和精修的对象

DeerFlow 1.x 的调研链路里，报告质量只在最后被评估一次，评完流程就结束了。 这个预研想验证一件事：如果把「评估」从终点搬到循环里， 让报告持续被检索、批评、重写，质量能不能真正抬上去。

01问题

计划、执行、成稿三段是割裂的

原流程是「规划 → 检索 → 写作 → 评估」的直线。评估只发生在最后， 它产出的分数不会回流到任何一步——报告写完了，旅程就结束了。

这导致两个具体问题。第一，检索是按计划执行的，不是按缺口驱动的： 计划里没想到的角度，后面不会补；第二，质量问题没有归因： 最后评出来 7 分，但没人知道是缺信源、逻辑断，还是引用不对。

我想验证的假设很简单：如果把报告本身作为循环里的中间产物， 让「缺口识别」和「批评」成为下一轮检索与改写的输入，那么同一套模型能产出更好的成稿。

一个类比

这套「先定位缺口、再定向补信息、然后重写」的流程，形式上很像扩散模型的去噪过程： 每一轮不追求一次到位，只求把当前草稿里最明显的那部分噪声减掉。 区别在于噪声是语义层面的——缺口、矛盾、无支撑的论断。

编排结构

Supervisor 是唯一的中枢，四个专职 Agent 都是它的工具，不是它的对等节点。

四个关键设计

这个项目最值得写的不是「用了多智能体」，而是每个角色的输入输出被怎么定义。
Design 01Supervisor 是唯一的中枢

三层 StateGraph 的调用结构里，只有 Supervisor 拥有调度权：它读 State、选一个动作、 调用对应 Agent、把结果注入回 State。四个专职 Agent（Researcher、Writer、Evaluator、Red Team） 互不直接通信——这样避免了多智能体系统里常见的「互相等待」和「循环对喷」。

Writer 与 Evaluator 之间的顺序也是 Supervisor 决定的：有时候先评再改（信息已经够，只是没写好）， 有时候先补再评（缺口太大，改了也白改）。

Design 02增量去噪，而不是重写

Writer 不是「根据一个问题写一份报告」，而是「根据累计 findings 和当前草稿，产出修订稿」。 这个输入设计很关键：它让 Writer 有能力保留上一轮已经写对的部分，只改有问题的地方， 否则每一轮都会退化成从零重写，反而越改越糟。

Researcher 的输入同样不是原始问题，而是被指认出来的缺口—— 「缺少 2023 年之后的数据」「这一段没有引用」比「再查一下」有用得多。

Design 03评估与红队，职责分离

Evaluator 从全面性、准确性、连贯性三个维度打分并记录，它的输出是数值； Red Team 则专门针对完整性缺口、主题一致性、逻辑自洽性生成批评。

分开的原因很实际：让一个角色既打分又提意见，它往往会给一个中庸的分数加一句正确的废话。 拆开之后，评分用于判断「还要不要再迭代」，批评用于指导「下一轮改什么」， 两者进入 State 的字段也不同。

Design 04状态管理与终止

跨层状态用 TypedDict 定义结构、Pydantic 做运行时校验、Reducer 负责研究结果的聚合 （多路检索返回的片段要合并去重，而不是覆盖）。

终止条件设了三重：主 agent 判断已完成、本轮无工具调用、或达到 15 次 Supervisor 决策上限。 第三条是成本兜底——没有硬上限的反思循环在生产环境里是不可接受的， 它会为了 0.1 分反复跑二十轮。

## 3. 训练侧的主要分歧

在冷启动数据的构造上，两类做法分歧明显：一类主张用强模型批量合成， 另一类坚持从真实交互里筛。[7] 前者成本低但分布偏平，后者噪声大而覆盖真实长尾。[12]

值得注意的是，已有工作对「拒绝采样」的阈值设定几乎没有公开讨论[19]， 而这恰恰决定了样本的难度分布——这一点在本轮调研中未能找到直接证据。

—— 标注为灰色的句子是 Red Team 指出的缺口，Writer 保留了它并显式说明「未找到证据」， 而不是编一个来源补上。

一个意外发现

最有价值的改动不是加了 Evaluator，而是让 Writer 在证据不足时保留不确定性。 原链路倾向于把话说满，因为没人会因为它编造而惩罚它； 有了红队之后，编造会被下一轮指认出来，于是模型学会了写「这一点没有找到可靠来源」。

从报告「好看」的角度这是退步，从可用性角度这是进步——一份知道自己哪里不确定的调研报告， 比一份通篇自信的报告有用得多。

评估维度看什么
全面性是否覆盖问题的各个侧面
准确性论断是否有引用支撑
连贯性章节之间是否有推进关系
边界

8.84/10 是内部实验样例的口径——同一批样例、同一套评分提示词，由 Evaluator 打分， 不是人工盲评，也不是公开 benchmark 上的分数。34 个信源是单份成稿的统计。 作为预研，它的价值在于验证了「评估回流」这个机制可行， 以及沉淀了可复现的 Notebook 运行轨迹与样例报告；它没有回答「相比基线的提升有多大」这个问题—— 严格的对照实验需要固定模型版本、固定信源与人工标注，这在实习期内没做完。

05我的部分

做了什么，没做什么

这个预研由我独立完成：从读 DeerFlow 1.x 的调研链路、找出现在单节点评估的断点， 到设计 Supervisor 调度结构、实现四个角色的输入输出与状态管理，再到跑通端到端样例、 沉淀运行轨迹与样例报告。

它没有进入生产——这是一次预研，结论以原型与实验样例的形式交付， 用于判断「报告质量优化」这条路值不值得投入。 也因此，这个项目里最硬的部分不是模型效果，而是流程设计： 谁在什么时候拿到什么输入、什么时候该停。
