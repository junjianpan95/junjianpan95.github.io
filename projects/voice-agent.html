Function Calling · MCP · 意图召回

基于分层 Function Calling 与 MCP 的小度智能家居语音 Agent

智能终端的语音助手面临的不是「能不能回答」，而是「技能太多」。把全部工具塞进一次 LLM 调用， 延迟、误匹配、无法拒识三个问题会同时爆掉。我们的解法是分层收敛： 小模型把范围缩小，大模型在范围内做对，MCP 把结果落到设备上。

01问题

技能极多，但每句话只命中一两个

终端可控制的部件、可打开的应用、可调用的服务累计数百项。全量注入 LLM 的工具列表， 会产生三个直接后果：延迟不可接受、误匹配率上升、无法拒识。

工具定义本身就有十几万 token，首字延迟从百毫秒级涨到秒级； 相似技能（「打开车窗」/「打开天窗」/「打开车窗一点缝」）互相干扰； 而当用户说了一句不该响应的话——车内闲聊、电视声音、无意义短句——系统仍会强行匹配到某个技能。

这三个问题在工程上是同一个问题的三种表现：候选空间远大于一次调用能承载的容量。 所以解法不是换更大的模型，而是先做减法。

分工原则

小模型负责「把范围缩小」，大模型负责「在范围内做对」。 意图召回与拒识都是判别任务，用 BERT 量级的模型就能做到毫秒级， 没必要让一个生成模型去猜「这句话归哪一类」。

端到端链路

从一句语音到设备动作，中间要过四个关卡：改写、拒识、召回、调用。

四个关键设计

前两个解决「选得对」，后两个解决「不乱选」和「执行得稳」。
Design 01用小模型把候选收到 Top5

基于智能家居业务数据微调 BERT-Large 做 439 类意图分类，取 Top5 后按意图—工具映射表 收敛出 20–40 个候选工具，避免把 455 个工具全量注入 LLM。

这里的取舍很清楚：acc@5（0.975）而不是 acc@1 才是这条链路的天花板—— 只要正确工具进了子集，LLM 还有机会在范围内选对；一旦漏在外面，后面全部失效。 所以训练时我把召回放在第一位，Top1 的 0.857 是顺带的结果。

Design 02MCP 作为执行底座

工具定义、参数 Schema、执行与错误返回统一走 MCP：Agent 侧只关心「调用哪个工具、传什么参数」， 设备差异被封装在 Server 里。参与了终端 MCP Server 的原型研发，完成工具 Schema 设计、 服务封装与 Client/Server 联调，打通「语义理解—工具调用—执行结果—播报」全链路。

这样做的直接好处是加技能不用改链路：新增一个设备能力，只需注册 Schema 与实现 Server 侧方法， 意图模型与映射表增量更新即可。

Design 03拒识：先改写，再判断

用 BERT-Tiny 做二分类拒识，拦截环境对话与无效输入。但单纯的拒识会误伤一种情况： 用户上一轮问「主卧空调多少度」，下一轮只说「调高一点」——这句话单独看很像无效输入。

所以拒识放在多轮 Query 改写之后：先把省略与指代补全成完整意图，再做相关性复核。 这个顺序调换把「省略追问被误拦截」的情况压了下来，也是多轮整轮正确率能到 88.6% 的原因之一。

Design 04槽位标准化与执行前校验

LLM 输出的槽位是自由文本——「二十六度」「26」「26℃」都可能出现。 执行前统一做数值归一、单位换算与枚举对齐，再校验参数是否在设备支持的范围内， 不在范围内就转澄清而不是硬发命令。

这一步看起来琐碎，但它决定了系统是「偶尔能演示」还是「可以给用户用」。

为什么 acc@5 比 acc@1 更重要

多层链路的误差是串联的。意图召回漏掉正确类，LLM 那一层无论多准都无法挽回； 反过来，只要正确工具在子集里，LLM 有能力把它挑出来。

这也是为什么多轮整轮正确率（0.886）会低于单轮 NLU 的槽位准确率（0.916）—— 每一轮都要对，误差会被轮数放大。要提升端到端，优先修的是第一层，而不是换更大的模型。

边界

四组数字来自不同环节、不同时间点的独立评测，不是同一次全链路压测的结果。 端到端一档按「一轮内意图与全部槽位均正确」的人工标注口径统计， 样本为 242 条多轮 case 共 509 轮。测试集规模有限，且场景集中在智能家居， 对开放域闲聊的拒识表现没有充分覆盖。

05我的部分

做了什么，没做什么

我在这条链路上负责 NLU 的整体设计、意图与拒识模型的训练、离线评测体系， 并参与终端 MCP Server 的原型研发与 Client/Server 联调。

需要说清楚的是：意图分类与拒识模型是在已有业务数据上微调的， 数据标注与清洗是团队协作的结果；MCP 协议本身的接入由平台侧提供， 我做的是工具 Schema 设计与服务封装这一层。设备侧的真实执行不在我的范围内—— 我负责的是「理解对了，并且把正确的调用发出去了」，执行是否成功由设备端回执确认。

这个项目后来也影响了我做 AIOps Agent 的思路：先算清楚候选空间有多大， 再决定哪一层用什么模型——这个判断顺序在那边同样成立。
