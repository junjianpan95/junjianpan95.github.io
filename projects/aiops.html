AIOps 故障诊断 Agent：把决策底座换成自己训的 9B 小模型

线上故障排查依赖 SRE 经验，响应慢、结论不可复现。我们先用双 Agent 把 「告警 → 根因 → 处置」做成闭环，再把闭环里本来就存在的确定性判定改造成奖励信号， 用 SFT + GRPO 训练一个可私有化部署的故障处置模型。

01问题

故障诊断是长程工具调用，不是一次问答

给定一条告警，Agent 要自己检索指标、日志、链路，交叉验证后定位可疑服务与根因类型， 再判断该走自动修复、提交 PR 还是转人工。

这类任务用商用大模型（如 Claude Opus）驱动时效果是够用的，但在生产环境里遇到三条硬约束： 成本（每次排查几十轮工具调用）、时延、以及数据不能出域。

另一个容易被忽略的问题是不可复现：同一条告警，两次排查的路径可能完全不同， 结论对不上时没人能说清是模型判断错了，还是这次观测到的信号本来就不一样。

为什么不用 LLM-as-judge 做奖励

自训小模型最直接的做法是请一个强模型给轨迹打分。但 judge 的偏好会漂移， 而且它本身也在猜「什么算诊断正确」——用它训出来的模型，学到的是模仿 judge，不是学会诊断。

我们的做法是回到系统里找已经存在的确定性判定：工具白名单的放行/拦截、 输出 schema 的结构化校验、终止条件判定。这些原本用于安全兜底， 天然对齐「这次处置是否合规、是否可执行」，而且零标注、不漂移。

系统架构

左半是诊断 Agent 的 ReAct 循环，右半是它唤起修复 Agent 后的直线流程。

四个关键设计

重点不是「用了 GRPO」，而是奖励从哪来、护栏放在哪一层。
Design 01分级处置：能现场恢复的不改代码

故障分两类：一类是资源水位、依赖抖动、发版引起的，就地操作就能恢复； 另一类是代码缺陷，只能改代码。前者按风险等级走白名单自动执行（滚动重启、重建 Pod、扩容）， 后者才唤起修复 Agent。这样避免了「一个重启能解决的事，跑成一次完整的改码 + PR 流程」。

高风险操作（改配置、删数据、动网络策略）不自动执行，转为工单并附上诊断轨迹， 由人确认。护栏是硬编码的，不依赖模型自觉。

Design 02把方法论和记忆外部化

四类经典故障（内存泄漏、依赖故障、发版回滚、配置错误）的排查步骤被写成 Agent Skills， 按告警语义动态加载，而不是全量塞进系统提示词——这一点和语音 Agent 里收敛工具集是同一个思路。

每次诊断结束后，轨迹被向量化写入 Milvus 形成经验库，封装成一个检索工具， 由模型自己决定什么时候去查。相同形态的故障第二次出现时，检索能直接给出「上次是哪一步定位到的」。

Design 03Schema 三级审查

SDK 层规定 Agent 输出的结构，编排层做三级处理：raw 文本校验（能否解析成约定结构）→ prompt 重试（解析失败时把错误回灌给模型重写一次）→ 兜底降级（仍失败则退化为只出诊断报告，不执行任何操作）。

这层审查不只是工程保险，它同时是训练信号的来源—— 哪一级被触发、校验是否通过，都是确定性的、可复算的。

Design 04复用工程判定做零标注奖励

奖励由三部分组成：结果正确性（service / kind / route 是否命中）、 过程合规性（Hook 的放行/拦截结果）、格式合法性（Schema 校验是否通过）。 三者都不需要人工标注，也不依赖另一个模型来打分。

同时设了四类反 reward hacking：重复动作惩罚、空转惩罚、越权尝试惩罚， 以及对「不做事但格式完美」这类退化解的抑制——否则模型很快学会只输出一份格式正确、内容空洞的报告。

怎么读这张表

SFT 提升的是「会说」，GRPO 提升的是「会判」。 从数据看，SFT 在 kind 上的涨幅（0.52 → 0.68）明显大于 route（0.36 → 0.46）—— 因为格式与常见根因可以模仿，而「该不该自动动手」需要权衡风险，靠模仿学不出来。 GRPO 之后 route 从 0.46 跳到 0.64，是这三项里相对涨幅最大的一档。

另一个值得注意的点是 MTTR：GRPO 版（2.00 min）比 Opus（2.62 min）还低， 尽管它的准确率更低。原因是小模型很少绕路——它在训练里学会了少做几轮无效探查， 而准确率更高的 Opus 会为了确认结论多跑几轮工具。

边界

评测集只有 13 个场景 25 条样本，量级偏小，单条样本就能带来 4% 的波动， 因此上表的差异应当看趋势而不是小数点。 另外四项指标的分母不同（修复成功率分母 6，代码定位 5，PR 提交率 5）， 跨行比较需谨慎。「人工 40 分钟」引用的是行业公开均值，不是本项目内做的人工对照实验。

05我的部分

做了什么，没做什么

这个系统的决策层由我从需求定义一路推到上线：架构设计、Skill 与护栏体系、数据构造、 奖励函数、训练与评测，以及最后的 vLLM 服务化接入。上游的 AIOps 平台（告警接入、工具层、执行侧） 是已有的基础设施，我写的是它上面的决策层。

有两点值得如实说明：一是 SFT 数据来自强模型在真实环境里的轨迹， 所以模型的起点是「模仿一个会排查的模型」，而不是从零学会排查； 二是 奖励函数依赖上游 Hook 与 Schema 的判定质量， 上游护栏写得越细，训练信号就越密——这也是我认为这套方法可迁移的原因： 任何有强工程约束的 Agent 系统，都自带一套没被用起来的奖励。
